## 1. 开场：30 秒 / 2 分钟 / 5 分钟三种讲法

### 1.1 30 秒版（电梯陈述）

> 这是一个 B 站直播间弹幕采集与分析工具，我用 Python 做后端、Vue 3 做面板。
> 它最有意思的部分是**协议层是逆向出来的**：B 站直播的弹幕走 WebSocket，是自定义二进制封包，
> 压缩后还是嵌套的同格式包，而且部分接口有 WBI 签名风控。
> 我把这些实测结论固化成金样本回归测试，做到**781 项测试全部离线可跑、核心模块覆盖率 90.76%**。
> 另外它的工程边界划得很清楚：采集链路是"神圣"的，面板和分析功能都不许影响它。

### 1.2 2 分钟版（推荐，覆盖技术纵深 + 工程素养）

按这个顺序讲，每段一句半：

1. **问题**：B 站直播间的弹幕数据在平台上留不住，想看历史、想统计就得自己采。
2. **范围收敛**：只采「有用户文字内容」的事件（弹幕 + SC），礼物/上舰/进房被过滤但**仍计数** —— 要能看到"漏了多少"，而不是无声丢弃。
3. **协议栈**：16 字节大端包头 + protover 0/1/2/3（原文/zlib/brotli）+ op 2/3/5/7/8；**解压后还是带头部的包，必须递归拆包**；心跳负载是字面量 `[object Object]`；`getDanmuInfo` 匿名必被 -352 风控，登录态叠加 WBI 签名才通，失败降级到匿名的 `getConf`。
4. **可靠性**：连接状态机 + 指数退避 + flap guard；**用"多久没收到心跳回应"判假死，而不是"多久没收到消息"**（低热度房间消息稀疏，按消息判会疯狂重连）。
5. **落盘**：四个 sink 各有独立有界队列和消费协程，满了**丢最旧并计数**；四格式条数在压测里严格相等。
6. **面板**：实时走 WS 广播，每个订阅者独立有界队列，**连续丢弃超阈值直接断开**——面板不许反向影响采集。
7. **复盘器**：历史用 `(recv_ts, id)` 复合游标翻页（不是 OFFSET），返回**瘦投影**（257 B vs 完整事件 2 KB）。
8. **分析**：词频在热路径增量维护（47 µs/条），跨片比较类指标放到请求时算；**数据不支持结论时明确返回"不可用"**（`rate_available=false`），不编数字。
9. **工程**：781 项测试离线可跑、覆盖率门禁 85%、`-m live` 才联网；假服务端 + 真实抓包夹具 + 20 万行合成库做性能门槛。

### 1.3 5 分钟版

在 2 分钟版上，把下面三块各展开 40 秒：

- **协议逆向的方法论**（见 §4）：`probe --dump-raw` 抓帧 → 写金样本 → 改 parser → 加回归。并主动讲 **R1–R7：设计文档被实测推翻的 7 条假设**。
- **性能决策的实证链**（见 §6）：先跑基线脚本拿数量级 → 定方案 → 看 `EXPLAIN QUERY PLAN` → 实现 → 用性能门槛验收（单页 < 200 ms 实测 18 ms）。
- **缺陷档案**（见 §10）：挑 D1（重连风暴）、D17（同步写阻塞事件循环）、D19（CSV 无 BOM 在 Excel 里乱码）三条讲，它们分别代表异步、并发、编码三类典型问题。

## 3. 架构主线：一次数据流的完整旅程

### 3.1 一句话架构

```
api.py 取房间信息与 token
  → client.py 建 WS、认证、心跳、收包
  → protocol.py 拆包解压（递归）
  → parser.py 归一化成 Event
  → filters.py 规则过滤（content_only 默认开）
  → collector.py 去重
  → sinks/bus.py 扇出给各 sink 独立有界队列
  → jsonl / csv / txt / sqlite   +   server/hub.py（WS 广播给面板）
```

### 3.2 讲解要点（每一条都是"设计意图"而不是"我写了啥"）

1. **协议层与业务层解耦**：`protocol.py` 只认字节、`parser.py` 只认 JSON。
   好处：协议层可以完全离线单测；协议变更时**定位范围是可判定的**。
2. **原始消息永远保留**（`Event.raw`，可 `--no-raw` 关闭）：
   字段位置变了可以**事后重新解析历史数据**，不用重抓。这是"协议会漂移"的直接对策。
3. **面板不是依赖，是消费者**：`WebHub` 只是 bus 的一个订阅者。面板挂掉、变慢，
   采集与落盘完全不受影响 —— 这条在 `hub.publish()` 里被硬编码为"慢客户端直接断开"。
4. **`store.py` 只读**（`file:...?mode=ro`）：分析/导出是**读**操作，不该有能力写坏采集数据。
   代价：加列必须走 `sinks/sqlite.py` 的 `MIGRATIONS`，且只读查询要**列自适应**（这就是 D18）。
5. **标注存独立库**（`annotations.db`）：采集产物与人写标注**生命周期不同**；
   `store.py` 只读、`annotations.py` 可写，刻意不合并。好处：清空标注 = 删一个文件。
6. **分析与采集分层**：`analysis.py` 是纯函数（无 IO / 无网络 / 无全局状态），
   有界聚合在 `hub.LiveWindow`。**跨片比较类指标（热点突增、账号画像）放在请求时算** ——
   它们不可加，一天算几次就够。

### 3.3 会被追问的点

- *"为什么不用消息队列 / Redis？"* → 单机个人工具，**引入外部依赖的收益小于运维成本**；
  需要的是**进程内**的故障隔离，`asyncio.Queue` + 独立消费协程已经买到。
- *"为什么不用 ORM？"* → 只读查询 + 四种落盘格式，SQL 很直白；
  ORM 反而会藏住 `EXPLAIN QUERY PLAN` 这个**本项目最重要的优化依据**。
- *"为什么不用 Kafka/ClickHouse？"* → 数据量级（本机库 79 MB / 1.7 万事件）根本不需要。

## 4. 协议逆向：本项目最硬的资产

### 4.1 封包格式（必须能画出来）

```
偏移  长度  类型     含义
0     4    uint32   包总长度（含 16B 头）
4     2    uint16   包头长度，固定 16
6     2    uint16   protover
8     4    uint32   operation
12    4    uint32   sequence
16    ..   bytes    负载
```

- **大端序**，代码里就是 `HEADER = struct.Struct(">IHHII")`。
- `operation`：**2** 心跳(C→S)、**3** 心跳回应(S→C)、**5** 通知(S→C)、**7** 认证(C→S)、**8** 认证回应(S→C)。
- `protover`：**0** 原文 JSON、**1** 心跳、**2** zlib、**3** brotli。
- **认证包必须在建连后 5 秒内发出**；心跳间隔 30 s（服务端 60 s 无心跳会强制断开）。

### 4.2 三个"必须讲"的实测结论

1. **递归拆包是必需的，不是优化**
   `protover=2/3` 解压出来的**仍然是一串带 16 字节头的包**。
   一次解压只到"包序列"，还要继续拆到 `protover=0` 才是 JSON。
   *佐证*：假服务端一开始压了裸 JSON，客户端正确地报出「包长越界」—— **客户端是对的**。

2. **心跳负载是字面量 `[object Object]`**
   这是 B 站网页端的实际行为（服务端不校验内容）。心跳回应 `op=3` 的**前 4 字节**大端 uint32 是人气值。
   *讲法*：这类"反直觉的实测事实"正是必须留样本、不能凭记忆写代码的原因。

3. **`getDanmuInfo` 匿名必被 -352，登录态 + WBI 签名才通**
   - `getConf` 匿名可用 → 保底路径；
   - 登录态下 `getDanmuInfo` 仍需**叠加 WBI 签名**（所以 `wbi.py` 是必需组件，不是备选）；
   - `-352` **绝不重试**（重试会加重风控），而是记入进程内黑名单并降级；
   - **token 每次重连都重新取**（会过期）。

### 4.3 WBI 签名（三段式，能讲清就说明你读过实现）

1. 匿名调 `nav` 拿 `wbi_img.img_url` / `sub_url` → 取文件名去 `.png` 得 `img_key` / `sub_key`（**每日更替，缓存 1 小时**）。
2. `raw = img_key + sub_key`，按 **64 项 `MIXIN_KEY_ENC_TAB` 重排后取前 32 位** = `mixin_key`。
3. 参数加 `wts`（秒）→ 按 key 升序 → 值过滤 `!'()*` → URL 编码（**百分号大写、空格是 `%20` 不是 `+`**）→ 拼 `mixin_key` → **MD5 = `w_rid`**。

**最值得讲的一条工程细节**：`encode_uri_component()` 是**手写的 JS `encodeURIComponent` 语义**，
并且有**官方金向量逐字断言**：

```python
enc_wbi({"foo": "114", "bar": "514", "zab": 1919810}, IMG, SUB, wts=1702204169)
  == "bar=514&foo=114&wts=1702204169&zab=1919810&w_rid=8f6f2b5b3d485fe1886cec6a0be8c5d4"
```

> 这是一个**向外标准对齐**的正确做法：算法类代码不能"看起来对"，要有已知输入输出。

### 4.4 解析层：结构化优先 + 下标兜底

- `DANMU_MSG` 的正文字段在新版里位于 `info[0][15].user`；其中 `info[0][15].extra` 是
  **JSON 字符串**，必须二次解析。
- 归一化字段（`text` / `uid` / `uname` / `server_ts` / `user_level` / 粉丝牌 / `guard_level` …）
  都是：**优先结构化对象 → 缺失才回退位置下标 → 用 `field_source` 标注来源**。
  `field_quality`（结构化命中率）是**协议漂移的早期预警指标**。
- **未知 `cmd` 走 `other` 兜底，绝不丢消息**。
- 去重键首选 `info[0][15].extra.id_str`（**全局唯一**），退化时用内容哈希 + 时间窗。

### 4.5 无依赖 protobuf 子集解析

`INTERACT_WORD_V2` 把数据塞进了 base64 编码的 `data.pb`，于是自己写了一个
**通用 wire-format 解析器**（`protobuf_lite.py`，无第三方依赖）。

**讲这一块的价值在于边界意识**，模块 docstring 自己写得很清楚：

> 「不保证语义正确性 —— 字段号的含义仍需按实抓样本确认。
> 本模块的价值是『**不丢数据 + 可检视**』，而不是『猜出字段含义』。」

并且嵌套判定是**保守启发式**（负载若恰好是纯可打印 ASCII 就保留为字节串、不递归）——
**宁可少解一层，也不要把 URL 或昵称误当子消息**。

## 5. 可靠性工程：不容易坏是设计出来的

### 5.1 连接状态机

```
IDLE → CONNECTING → AUTH_SENDING → AUTHED → STREAMING ⇄ HEARTBEATING
                          ↓ 连续认证失败 5 次
                     RECONNECTING ──退避──→ CONNECTING
                          ↓
                       PAUSED（300 s 后再试）
```

关键参数与依据（**每个数字都有理由，讲的时候要说理由**）：

| 参数 | 值 | 依据 |
|------|----|------|
| 心跳间隔 | 30 s | 服务端 60 s 无心跳强制断开，留一半余量 |
| 假死判定 | 90 s 无 `op=3` | **用心跳回应判，不用消息判** —— 低热度房间实测 25 秒只有 11 条消息 |
| 读超时 | 5 s | 消息稀疏是常态，读超时**不能**当作断线 |
| 稳定阈值 | 5 s | 服务端"接受后立即断开"曾被当成一次成功，导致**重连风暴**（D3） |
| 退避上限 | 60 s | 上限封顶避免无限增长 |
| 认证失败上限 | 连续 5 次 → 暂停 300 s | 避免拿坏凭据去打风控 |

### 5.2 背压与故障隔离（本条最容易讲出水平）

- 每个 sink **独立的消费任务 + 独立有界队列**（默认 20000 条），队列满时 **丢最旧并计数**，
  **绝不 OOM**。
- **关键因果链（D17）**：sink 的 `write()` 是同步 IO。一开始它直接在事件循环线程里执行，
  磁盘一慢 → 事件循环被阻塞 → **心跳任务发不出去** → 采集器判假死 → 重连。
  现象非常误导："明明只是落盘慢，为什么整条连接重启？"
  **修法**：`Bus._flush_off_loop()` → `asyncio.to_thread`。
  **推论**：跨线程使用的 `sqlite3` 连接必须 `check_same_thread=False`（`SqliteSink` 与只读 `DanmakuStore` 都改了）。
- **刻意不给 `to_thread` 加超时**（讲这个细节很加分）：超时后线程**仍在跑**，
  下一批再进来就可能**并发使用同一个 SQLite 连接**。卡死的 sink 只该拖住它自己。
  所以真正的隔离手段是"每 sink 独立队列"，而不是"给写入加超时"。
- 单个 sink 连续失败 3 次 → 标记失败停用，**其余 sink 继续**，退出前汇总报告。

### 5.3 去重

三层：
1. 进程内 `DedupeCache`（有界 LRU + TTL，优先 `id_str`）—— 合并实时流与历史补种；
2. SQLite `UNIQUE(dedupe_key) ON CONFLICT IGNORE` —— **第二道防线**；
3. 因此 `event.id` 会有空洞 ⇒ **不能用 `id` 算总数**（这是一个很好的"细节坑"素材）。

### 5.4 优雅停止

三条路径：面板按钮 / `bili-danmaku web stop` / 兜底 `taskkill /F`（**会丢队列里未落盘的批次**）。

**这里有一个非常值得讲的 Windows 平台经验**：

> Windows 上"优雅停止"**不能靠信号** —— 实测三连：
> `CTRL_BREAK_EVENT` 对独立进程组的 uvicorn **8 秒无响应**；
> `taskkill /PID`（不带 `/F`）**Access denied**；
> 最终方案是**让服务自己退出**：控制端点 → `Server.should_exit` → lifespan 收尾 →
> 每个房间 `bus.stop()` **flush 落盘**。

## 6. 存储与查询：性能是量出来的，不是猜的

### 6.1 四种落盘格式与一致性验收

| sink | 特点 |
|------|------|
| JSONL | 每行一个事件，`ensure_ascii=False`，按小时/128 MB 轮转，已存在则 append |
| CSV | **`utf-8-sig`（BOM）**，Excel 双击不乱码；**做了公式注入防护**（`= + - @` 前缀） |
| TXT | `[HH:MM:SS] 昵称: 内容`，只含弹幕 |
| SQLite | WAL + `synchronous=NORMAL` + `busy_timeout=5000`；**一批事件 = 一个事务** |

**验收方式值得主动说**：M2 时抓 114 条，**四格式条数完全一致**；
`replay` 离线转换的结果与原始 CSV **逐字节一致**；
压测（房间 7878，约 300 条/分钟，90 s）得到 **179 = 179 = 179 = 179**。

### 6.2 为什么历史分页不用 OFFSET（双理由）

1. **正确性**：`recv_ts` 会并列 —— 实测房间 804456 有 **393 组重复时间戳、最多 10 条同刻**。
   只用 `recv_ts` 做游标会在页边界**漏条**。
   ⇒ 用 **`(recv_ts, id)` 复合游标**，并且 **`ORDER BY` 必须与游标键同键**（都是 `recv_ts DESC, id DESC`）。
   若排序键与过滤键不一致，**同样漏条**。
2. **性能**：OFFSET 分页在大偏移下退化成近秒级扫描，且随库增长近似线性劣化。
   实测 `iter_events(limit=100400)` 级别的大 offset 路径要 **3.6 s**。

**查询计划实测**（20 万行合成库 + 真实库）：

| 写法 | 计划 | 耗时 |
|------|------|------|
| 复合游标 + `room_id`（本实现） | `SEARCH ... COVERING INDEX idx_event_room_ts`，**无临时排序** | 首屏 400 条 **18 ms** |
| `ORDER BY id DESC` 游标 | 索引 + `USE TEMP B-TREE FOR ORDER BY` | 12.3 ms |
| 无 `room_id` 过滤 | `SCAN` + 临时 B 树 | 39.8 ms/页 ⇒ 必须有兜底时间窗 |
| 密度 `GROUP BY CAST(recv_ts/b AS INT)` | 索引 + 临时 B 树 | 118 ms |
| 密度 `GROUP BY recv_ts, type`（本实现） | 覆盖索引 | **38 ms** |

> **这张表就是"先量再做"的证明**。新增索引 `idx_event_room_ts_type` 让密度聚合 118 → 38 ms；
> 把"折算桶"从 SQL 挪到 Python（行数 = 不同时间戳数，远小于事件数）也是同一个测量结论的产物。

### 6.3 瘦投影：载荷宽度是设计决定

- 完整 `Event`（含 `raw_json`）实测 **≈ 2.0 KB/条** ⇒ 400 条一页接近 **800 KB**，
  浏览器解析成本高，而且**很容易把自己变成服务端的慢客户端**（会被主动断开）。
- `HISTORY_COLUMNS` + `_project()` 只保留展示必需字段，实测 **257 B/条** ⇒ 400 条从 ~800 KB 降到 ~100 KB。
- **契约纪律**：`/api/history` 等**新增只读端点**默认返回瘦投影；
  `/api/events` 与 `/api/export` 保持**完整 `Event`**（它们是与脚本/导出的通用契约，**宽度不能悄悄变窄**）。
  有回归用例守着这条（`test_history_items_are_narrower_than_events`）。

### 6.4 为什么不用 FTS5（明确的设计偏离）

- `unicode61` 分词器把连续中文当 **一个 token** —— 搜「主播」匹配不到「主播好」；
- `trigram` 又要求查询 **≥3 字符**，而中文关键词常为 **2 字**（「哈哈」「主播」）。
- ⇒ 统一走 `LIKE '%kw%'` 子串匹配（**并转义 `%` / `_` 通配符**）。

**这个结论写在 `store.py` 的 docstring 里**，是"实测推翻了设计文档"的典型例子
（`DESIGN.md` 原本计划建 `event_fts` 虚拟表）。

### 6.5 schema 迁移的三处纪律（很好的"工程严谨性"素材）

给表加一列要**同时管三处**：
1. `sinks/sqlite.py` 的 `SCHEMA`（新库）；
2. `MIGRATIONS`（老库 ALTER，因为 `CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做）；
3. **只读层的自适应查询**（`DanmakuStore` 是 `mode=ro`，**永远不会跑迁移**，所以要 `has_column()` 降级）。

> 第 3 条就是 **D18**：V2 词云首次运行在老库上报 `no such column: extra_json`，功能完全不可用。

## 7. Web 与前端：把边界划清楚

### 7.1 服务端

- FastAPI + uvicorn；REST + WS 一体；**端口被占用自动向后找**（8787 → 8788… → 系统分配），
  并且**一定打印实际 URL**。
- **前端未构建时返回内建提示页**，REST/WS 完全不受影响 ——
  「面板不该因为缺 Node 而让整个工具不可用」。
- 安全默认：绑非回环地址必须配 token，否则**拒绝启动**；
  控制端点 `POST /api/admin/shutdown` **仅回环 + Origin 校验 + 仅 POST**。

### 7.2 WS 广播中枢（`server/hub.py`）

- `publish()` 是**同步**接口 —— 因为它在 sink 工作协程里被调用，**绝不能阻塞**。
  顺序：序列化 → 环形缓冲（2000/房间）→ 分析窗口 → 累计计数 → 逐订阅者 `accepts()` + `put_nowait`。
- **每个订阅者独立有界队列**，满了丢最旧并 `dropped++`；
  累计丢弃 ≥ 200（`SLOW_CONSUMER_DROPS`）⇒ 发 `SLOW_CONSUMER` 错误消息后**主动断开**。
  **一句话讲清设计意图**：「面板是采集的消费者，它不该反向影响数据完整性。」
- `accepts()` 是 `publish()` 与 `recent()` **共用的一处判定**（D13 的修复：
  历史回填曾经绕过订阅过滤，订阅 `types=danmaku` 却先收到互动/点赞）。

### 7.3 前端关键取舍（挑 4 条讲）

1. **双层数据流**：实时层环形缓冲（2000 条，进入历史浏览时**收缩到 300**）
   + 历史层按游标翻页，合并视图按 `id` 去重。
   **明确拒绝的错误解法**：把缓冲从 2000 提到 50000 —— 既崩内存又崩渲染，
   而且**翻不到更早的会话**。
2. **类型过滤在客户端做，切换不重连**：服务端也支持 `types=` 订阅过滤，
   但那样每次改动都要重连并丢掉已缓冲内容；**只有切换房间才重连**。
3. **绝不 `v-html`**：弹幕正文是不可信用户输入，关键词高亮走**分段渲染**；
   表情图片**只接受 `http(s)` 地址**（挡掉 `javascript:`）。
   手测清单里有一条就是发 `<img src=x onerror=alert(1)>` 验证它**不会被解释**。
4. **向上翻页补偿 `scrollTop`**：`StreamList.preserveAnchor()` 必须先记 `scrollHeight`、
   `nextTick` 后按差值补 —— **只记 `scrollTop` 不够**（内容变高后它的语义已经变了）。

### 7.4 两个"产品语义"级的设计（讲出来很出彩）

- **`has_newer` 是本地状态，不是照抄服务端**：
  服务端的 `has_newer` 只说明"这一页之后还有没有数据"。用户向上翻几页后窗口尾部
  已不含最新数据，服务端会算出 `false` ⇒ **照抄就再也翻不回最新**。
  正确语义是"窗口是否已离开实时边缘"（`detached`）。
- **打标记的时间点取"可见的最后一条弹幕"，不是墙钟**：
  若按墙钟取，用户在看历史时会把标记打到"现在"，而屏幕上显示的是几小时前 ——
  **这种错误从界面上完全无法察觉**。

## 8. 隐私与合规：一个真实的加分项

### 8.1 基线承诺

- 凭据只落本机 `.secrets/`（gitignore，权限收紧）或纯环境变量模式（**完全不落盘**）；
- **所有日志统一脱敏**：`RedactingFilter` + 「**已登记密钥**」表
  （凭据构造时把字面量登记进去，之后**任何位置出现都被替换**）；
  这是 D5 的修复 —— 只按 `key=value` 模式匹配抓不到"裸打印的 token"；
- **不保存账号资料**：只保留连接所需 cookie 字段，昵称/mid/头像一律丢弃；
- **项目不含任何上传逻辑**。

### 8.2 数据侧的自我约束

- 抓到的弹幕含**其他观众**的 UID 与昵称，属于第三方个人信息：
  数据默认只在本机，提供 `--anonymize`（uid 加盐哈希、昵称掩码）与 `--exclude-masked`；
- 平台打码结果**原样保留、不尝试还原**（便于统计"有多少条被打码"）；
- 本地分析结果"仅供参考、非判定"，面板上明确写着**数据不出本机**；
- 任何"外发数据"功能（LLM / Webhook）**必须先过 G4 —— 书面的隐私决策**，不是普通功能。

> **这一节为什么加分**：它证明作者把"能不能做"和"该不该做"分开了。
> 尤其 `RedactingFilter` 那条 —— 安全设计要假设人会忘记手动掩码。

### 9.1b 三类"金标准"用例（讲这些最能证明测试不是刷数量）

**(a) 协议异常路径逐字断言错误消息**（`test_protocol.py`，17 项）

```python
test_illegal_header_length_raises                → match="非法包头长度"
test_packet_length_smaller_than_header_raises    → match="小于头长"
test_trailing_bytes_raise                        → match="尾部残留"     ← 很多实现会漏这一条
```

外加**复刻实测字节**：认证回应 `bytes.fromhex("0000001a001000010000000800000001") + b'{"code":0}'`（总长 26 / 头长 16 / protover 0 / op 8）；心跳回应 `struct.pack(">I", 2466)` + 断言 `payload[4:] == b"[object Object]"`；还有 zlib 套 zlib **两层**的嵌套用例。

**(b) 游标"不重不漏"属性测试**（`test_history.py`，19 项）

数据构造 `build_db(rows=60, tied=3)`：时间戳由 `index // 3` 决定 ⇒ 末三条同刻；raw 造**真实的 1.6–2.4 KB 体积**（注释：「夹具必须带上它，否则『瘦投影省了多少字节』这类断言会被一个假的小 raw 骗过去」）。

```python

test_history_items_are_a_slim_projection
```

**(c) 背压的"守恒不变量"**（`test_collector.py` 尾部 3 项）

构造：`queue_size=4`、`batch_size=1`、`flush_interval=60.0`、`SlowSink(block_seconds=1.2)`、`total=12`。
**两个"实测踩过的坑"直接写在脚本注释里**：
- 「批大小必须为 1：否则 worker 会靠『get 超时』一条条攒进 batch，队列永远是空的（**实测踩过这个坑**），根本压不出背压。」
- 「**第一条就阻塞**：这样消费协程会卡在这里，队列只能等读循环去塞满它。」

断言的核心是**数据守恒**：

```python
assert stats.received == total            # 卡住的 sink 不该让读循环漏消息
assert stats.reconnects == 0              # sink 卡住绝不能拖到心跳
assert server.heartbeats >= 1             # 心跳必须照常发出
assert stats.dropped == worker.dropped    # 采集侧与 sink 侧计数一致
assert len(final) + stats.dropped == total                       # 写入 + 丢弃 == 总接收
assert [order.index(i) for i in final] == sorted(...)            # 写下来的是原序列的子序列
assert order[-1] in tail                                         # 丢的确实是最旧的
```

> 这套断言比"断言丢了几条"强一个量级：它钉住的是**不变量**，
> 而不是某次运行的偶然数值（注释里也明说「精确到个位数会不稳，契约是『丢了旧的 + 计数一致』」）。

**还有两条"双向断言"值得单独提**（回归测试的成熟做法）：
`test_suspicious_ignores_backfilled_history_with_identical_timestamps`（不该误报）
与 `test_suspicious_still_flags_identical_timestamp_repeater`（该报的仍要报）——
**同一个现象的两个方向都被钉住**，避免"修 A 弄坏 B"。

**测试基础设施的坑（也写在文档里，说明被认真整理过）**：
`TestClient` 的客户端地址是字面量 `'testclient'`（判来源的端点必须显式
`TestClient(app, client=("127.0.0.1", 51234))`）；`loop.call_later` 的回调在 `TestClient` 里**不会执行**
（要"响应后执行"得用 Starlette `BackgroundTask`）；`ipaddress.ip_address("::ffff:127.0.0.1").is_loopback`
是 **False**（要额外看 `ipv4_mapped`）；`Bus` 的队列容量在**构造时**固定；
模块级 `_TOP_SENDERS_CACHE` 会跨用例存活（需 `reset_top_senders_cache()`）；
夹具里 `msg_id` 必须唯一，否则会被 `UNIQUE(dedupe_key)` **正确地**合并，让你误以为"写丢了数据"。

### 9.2 覆盖率口径（口径本身就是一个可讲的决策）

- 门禁 **85%**，当前 **90.76%**（781 项）；
- **只统计核心模块**（协议/解析/连接/过滤/落盘/服务端/存储/网络接口）；
- **`cli.py` 与 `__main__.py` 不计入百分比** —— 命令编排混进百分比会让
  "核心逻辑有没有被测到"变得不可读；它们由 `tests/test_cli.py` 的端到端用例保证。
- GUI 的 `panel_window.py` / `tray.py` / `_win32.py` 同样排除，
  但**排除 ≠ 不测**：可测部分（菜单结构、置灰逻辑、状态文案、CLI 接线）仍在 `tests/test_gui.py` 里；
  只有"像素与点击手感"真的靠手测。

> ⚠️ 讲覆盖率时**主动说分模块最低值**（`collector.py` 71%），否则被追问会很被动。见 §13。

### 9.3 打包与分发（三个有含金量的坑）

1. **PyInstaller 冻结后 `find_dist()` 必然失败**：
   包被打进 `base_library.zip`，`bili_danmaku.__file__` 是**合成路径**、磁盘上没有该目录，
   所以"找包内 `web_dist/`"的候选必然落空。
   **修法**：`find_dist()` 增加冻结分支，把 `sys._MEIPASS / "web_dist"` 作为首选候选；
   打包参数用 `--add-data "<web/dist>;web_dist"`。
   **判据**：`verify` 必须看到 `served_real_frontend: True`，否则 exe 起来只有降级页。
2. **入口不能用 `cli.py`**：PyInstaller 把它当"顶层脚本"执行，
   `from . import __version__` 会报 `attempted relative import with no known parent package`。
   ⇒ 生成一个**绝对导入**的引导脚本作入口。
3. **`--windowed` 下 `sys.stdout/stderr` 是 `None`**：任何 `print()` 都会崩。
   而且此时 `setup_logging()` 只挂 `StreamHandler(sys.stderr)` ⇒
   **日志全部丢弃**（托盘完全没有可排查的痕迹）。
   **修法**：额外挂 UTF-8 `FileHandler`；冻结/无 stderr 时自动落 `.runtime/web.log`；
   并且**显式接管 uvicorn 的 logger**（`uvicorn.error` / `uvicorn.access` 是
   `propagate=False` 且自带 handler 的独立 logger，**不会**经过根 logger）。

### 9.4 工程约束的硬性记录

- `pytest` **必须保持离线可跑**（需要联网的用 `@pytest.mark.live` + 环境变量开关）；
- 排查/打包脚本（`tools/` 下 **37 个**）**不并进 pytest**（单次 20–60 s、产出几十 MB、需网络）；
  真正的回归保护在 `tests/`（例如冻结路径由
  `test_server_sqlite.py::test_find_dist_uses_meipass_when_frozen` 系列钉住）；
- 中文文件只用编辑工具改（PowerShell 的 `Get-Content -Raw | Set-Content` 会把 UTF-8 中文写坏，
  而且**吃掉换行** —— 这个仓库真的被毁过一次）。

### 9.5 `tools/` 这 37 个脚本该怎么讲（**别当成脚本堆**）

它们其实是**三类东西**，讲清分类比逐个念文件名有价值得多：

| 类别 | 数量 | 代表 | 作用 |
|------|------|------|------|
| **正式构建/验收** | 4 | `build_exe.py` / `build_wheel.py` / `make_icon.py` / `stress.py` | 出包与压测；`stress.py` 有明确退出码契约（0/1/2/3/4/5） |
| **一致性校验** | 4 | `verify_formats.py` / `verify_web_start_fix.py` / `verify_exe_log.py` / `check_timeline_start.py` | 把"用户报的 bug 修没修"变成**可重复执行的脚本** |
| **一次性探针/诊断** | 20+ | `diag_*`（pip/TLS 排障 7 个）、`probe_*`（进程/托盘/冻结布局 10 个）、`test_pyinstaller*.py`、`test_frozen_layout.py` | **把"猜"变成"实测"** |

**案例一：`probe_*` 构成一条完整的因果推理链**（这是整份材料里最能体现调试能力的一段）

缺陷是「关掉启动它的终端，面板也跟着停」，与 `DEC-3` 的承诺相反。排查过程：

1. `probe_job.py`：查"是不是 Job Object 的问题" → **证伪**（每层都在 job 里，且 job 允许 breakaway）；
2. `probe_spawn.py`：定位真凶 → venv 的 `python.exe` 是**转发器 stub**，它必须再起一个 base 解释器，
   而 base 是 console 程序又拿不到父 console ⇒ **Windows 新分配一个 conhost**；
3. `probe_console_owner.py`：用 `AttachConsole(pid)` 成功/失败判定"谁拥有 console" →
   **真 server 有 console，顶层 `Popen` 没有**；
4. `probe_kill_conhost.py`：**因果验证** —— 杀掉那个多余 conhost（等价于用户点窗口的 X），
   挂在它上面的真 server 约 5 秒后被杀；
5. `probe_base_exec.py` + `probe_real_panel.py`：验证修法（绕开 stub，直接起 base 解释器 +
   注入 `PYTHONPATH`/`VIRTUAL_ENV`/`PYTHONNOUSERSITE`，并**清掉 `PYTHONHOME`**）；
6. `verify_web_start_fix.py`：用**可自动化**的判据回归 —— ①面板 HTTP 可达 ②进程树里只有一个 python
   ③**没有 `conhost.exe` 作为 server 的子进程**。

> **这里最值得讲的不是"修好了"，而是"根因被推翻过一次"**：
> 第一版结论是 Job Object，`probe_job.py` 把它证伪了。
> `probe_frozen_layout.py` 的 docstring 甚至自己写着「把两种模式的真实目录布局打出来，**不猜**」。

**案例二：`wheel_fetch.py` 是一个手写的"约束感知"依赖解析器**

背景（写在 docstring 里）：本机 pip 的网络栈异常，但 `httpx` 完全正常 ——
所以用 httpx 自己实现"解析 + 下载"，再由 `pip --no-index --find-links wheels` 离线安装。

它的三段式结构本身就是一个小型包管理器：

| 组件 | 做法 | 亮点 |
|------|------|------|
| `wheel_score(filename)` | **打分制**兼容性过滤（cp311+abi3+win_amd64=100 / … / py3-none-any=50），不兼容返回 `None` | 比"字符串匹配 python tag"健壮得多 |
| `class PyPI` | 带重试（3 次、线性退避）+ 两级缓存（`{name}/json`、`{name}/{version}/json`）的元数据客户端 | 404 直接返回 `None` 而不是抛 |
| `class Resolver` | **约束传播求交集** + **worklist 不动点迭代** + 逐版本回溯；`merged = constraints[key] & spec`，**只有约束变化才重算** | **解决了真实冲突**：`pydantic 2.13.5` 要求 `pydantic-core==2.46.5`，第一版没做交集时装了 2.49.0 |
| `class Downloader` | `target.is_file() and size > 0` 就复用（增量下载） | — |

它还会按 `requirement.marker.evaluate(env)` **按环境求值**、跳过 `extra` 相关依赖、跳过 `yanked` 发行版，
并用 `passes < 2000` 封顶防死循环；根包清单是**追加而非覆盖**（注释：「覆盖会让 lock 文件丢掉项目依赖」）。
产物是 `wheels/` + `requirements.lock.txt`。

> **一句话讲法**：「因为环境的 pip 坏了，我用 httpx 写了一个能解依赖版本约束的下载器，
> 它解决的具体问题是『`pydantic 2.13.5` 要求 `pydantic-core==2.46.5`，而我第一次装成了 2.49.0』。」
> 这比说"我会用 pip"信息量大得多。

### 9.6 这里**没有**的东西（诚实，也是面试官会问的）

- **没有 CI**：无 `.github/workflows/`、无 Makefile/justfile/nox。

  全仓库 grep `github_version` **0 命中**）。看名字应是"预留的公开发布目录"，**但从未落地**。

  ⇒ 「装 wheel 开箱带面板」这条路径**只在 09-21 那一版被验证过**。

## 10. 缺陷档案：把 20 个 bug 讲成能力证明

> **讲缺陷的正确姿势**：现象 → 根因 → 修法 → **怎么防止再犯**。
> 下面 10 条是最值得讲的（完整 D1–D20 见 `TECH_DESIGN.md` 附二 / `HANDOVER.md` §8）。

### 10.1 异步与生成器（D1 / D2）

| # | 现象 | 根因 | 修法与防线 |
|---|------|------|-----------|
| **D1** | **2.5 秒内重连 26 次** | `asyncio.TimeoutError` **逃出**了 `messages()` 生成器 → 迭代器被终结 → 调用方下次取值拿到 `StopAsyncIteration` → **误判连接结束** | 读超时在生成器**内部**吞掉；只有心跳长时间无回应才抛 `ConnectionStale` |
| **D2** | `grab --duration` **死锁**（首个用例挂满 10 分钟） | 修 D1 时把截止判断放在了**外层循环**，而生成器只在**收到消息**时才交回控制权 ⇒ 无消息时外层永远等不到检查机会 | `should_stop` 回调**注入生成器内部**，每次读超时后检查一次 |

> 这两条连起来讲特别好：**第一个修复引入了第二个 bug**，
> 而第二个 bug（死锁）比第一个（重连风暴）更隐蔽。这体现的是"改异步代码要重新推演控制流"。

### 10.2 有界窗口与热路径（D17）

已在 §5.2 详述。补充一句总结：
**"慢 sink 导致重连"是这类系统最容易犯的架构错误 —— 把不可控的 IO 放进了对的线程之外。**

### 10.3 编码（D19）—— 最"涨知识"的一条

- **现象**：Web 面板导出的 CSV 用中文版 Excel 双击打开**全乱码**。
- **误导点**：文件本身是**合法 UTF-8**，用 Python 能正确读出中文 ⇒ 很容易误判成"数据写坏了"。
- **根因**：流式导出只写了 `utf-8`，**没有 BOM**。
  `Content-Type: text/csv; charset=utf-8` 对**双击打开的本地文件无效** ——
  Excel 只看文件头，没有 BOM 就按系统码页（GBK）解。
- **对照**：`sinks/csv_txt.py` 与 CLI `export` 一直用 `utf-8-sig` ⇒ **只有面板这一条路径坏**。
- **修法**：新增 `CSV_BOM`，**只加在第一个 chunk（表头）之前**
  （每块都加会在正文中间插入 `\ufeff`；JSONL/TXT **不能**加，会污染首行解析）。
- **防御**：字节级回归 `assert response.content[:3] == b"\xef\xbb\xbf"`；
  同时断言 JSONL/TXT **不带** BOM。
- **方法论**：**编码问题在 `pytest` 里天然测不出来** —— 断言 `response.text`
  拿到的是已经正确解码的字符串，中文当然"正常"。
  **凡是"交给别的程序打开"的产物（CSV/Excel、PNG、PDF），验收都要覆盖真实消费者怎么读它。**

### 10.4 金额单位（D20）

`--min-price` 曾把"元"门槛直接与所有类型的 `price` 比 ——
但 **SC 的 price 是元，礼物/上舰是金瓜子（1000 = 1 元）**，于是差了 **1000 倍**。
修法：按类型换算（`min_price_threshold`），并且**既有测试还把错误行为固化成断言**，
必须一起改。（这条的教训：**测试固化了错误的语义，比没有测试更危险**。）

### 10.5 "单测全绿但功能全废"（D12 / D13 / D15 / D16）

| # | 缺陷 | 为什么单测没抓到 |
|---|------|-----------------|
| D12 | `Subscriber` 放不进 `set` ⇒ **任何 WS 连接一建立就 500**。根因：`@dataclass` 默认生成 `__eq__` 并把 `__hash__` 置为 `None`。修法：`@dataclass(eq=False)` | 只有真的建立 WS 连接才会走到 |
| D13 | 历史回填**绕过订阅过滤** | 只有连上 WS 才走到回填路径 |
| D15 | **`/api/export` 实际 500（导出按钮全废）** | 测试配置里**没有 sqlite sink**，只跑到内存降级分支 |
| D16 | `export` / `replay` **不带 `--out` 时崩溃** | 从来没有跑过"输出到 stdout"这条路径 |

> **这四条是"必须做端到端验收"的最好论据**，也是本项目一条明文开发约定：
> 「**改过滤/落盘/连接逻辑后，除单测外必须做一次端到端验收**」。

### 10.6 安全缺口（D5）

脱敏过滤器原本只按 `key=value` 模式匹配 ⇒ 如果日志里**直接打印 token 本身**（不带字段名）就会泄露。
修法：引入「**已登记密钥**」表 —— 凭据构造时把字面量登记进去，**任何位置出现都被替换**。

> 讲法：「安全过滤要假设人会忘记手动掩码，所以正确的做法是**把需要保护的值登记起来**，
> 而不是去猜它会长什么样。」

### 10.7 顺序错会掩盖真错（D14）

`add_room` 先查房间号（打网络）再查并发上限。结果：已达上限时，用**不存在的房间号**
会报"房间不存在"，**真正原因被盖掉**，而且白打一次接口。
修法：**先做本地约束检查，再打网络**。

### 10.8 分析与"不能给用户假结论"（三处误报）

V3-b 的异常账号画像一度把**正常人**报成疑似异常账号，根因三条：

1. 历史补种把一批弹幕写成**同一时刻** ⇒ `count / span` 算出「600 条/分钟」；
2. 时间戳各不相同但**全挤在 1 秒内**（实测 10 条 / 0.9 秒）⇒ 同样荒谬；
3. **重复率公式写错**：`1 - 去重数/总条数` 使"10 条完全相同"只有 90%，永远够不到满值 ⇒
   改为 `1 - (去重数-1)/总条数`。

**第一条的第一次修复是错的**（加"窗口下限"会把真实爆发一起压平）。
**正解**：要求观测跨度 ≥ 30 秒，否则 `rate_available=false`，**直接放弃速率类结论**；
重复率与时间无关，仍参与打分。

> **这一条是最能体现工程价值观的**：
> 「做启发式评分时，**"数据不支持这个结论"必须能表达出来**。
> 硬算出来的数字会被用户当成事实，而**误报的代价（误伤真人）远高于漏报**。」

## 11. 高频追问与建议答法（34 问）

### A. 协议与逆向

1. **Q：为什么不用现成的第三方库（如 `bilibili-api`）？**
   A：这个项目的**核心价值就是协议层本身**；而且现成库大多是同步/拉取式，
   本项目要的是长连接 + 背压 + 多格式落盘的一整条链路。
   另外依赖越少，"pip 出问题"这类环境事故的暴露面越小（这也是托盘坚持零依赖 ctypes 的理由）。
2. **Q：怎么确认你的字段解析是对的？**
   A：`probe --dump-raw` 抓真实帧存成夹具 → 逐条断言归一化字段 → 这些夹具是**唯一可信依据**，
   文档写死都不算。改协议相关代码前必须先跑 `pytest tests/test_parser.py`。
3. **Q：B 站改协议了怎么办？**
   A：三层防线：①`raw` 全量保留，可**事后重新解析历史数据**；②未知 cmd 走 `other` 兜底不丢消息；
   ③`unknown_cmd` 计数与 `field_quality`（结构化命中率）是**早期预警指标**。
4. **Q：`-352` 是什么？为什么不重试？**
   A：是 B 站的风控码。**重试会加重风控**，所以策略是"记住并降级"：
   进程内把该房间加入黑名单，直接走匿名可用的 `getConf`，同时降低 HTTP 频率。
5. **Q：WBI 签名原理？**
   A：见 §4.3。要点是密钥每日更替（缓存 1 小时）、64 项重排取前 32 位、
   手写 `encodeURIComponent` 语义、**有官方金向量逐字断言**。
6. **Q：protobuf 为什么不用 `protobuf` 库？**
   A：①无 `.proto` 定义（字段号是逆向出来的），官方库也要 schema；
   ②只要子集解析，多一点依赖就多一份打包与版本成本；
   ③自研版的定位**明确**是"不丢数据 + 可检视"，**不承诺语义正确性**。

### B. 并发与可靠性

7. **Q：为什么每个房间一个连接而不是共享？**
   A：B 站协议本身就是"一个房间一条连接 + 一个 token"；共享会引入多路复用的复杂度，
   而带宽/连接数根本不是一个房间的瓶颈。
8. **Q：有界队列满了丢数据，能接受吗？**
   A：这是**刻意的取舍**。选择是"丢最旧 + 如实计数（`dropped`）" vs "阻塞读循环"。
   阻塞读循环会让心跳发不出去 → 被服务端断开 → **代价更大**。
   而且丢弃是**可观测的**（面板与 stats 都能看到），不是静默丢失。
9. **Q：为什么不用 `asyncio` 的线程池做落盘？**（其实用了 —— 要讲清区别）
   A：落盘的**编排**是 asyncio（队列 + 协程），只有**同步的阻塞写入**这一步
   通过 `asyncio.to_thread` 挪出事件循环。这是最小改动的正确切法：
   编排留在协程里便于优雅停止与 flush，只有会阻塞的那一段离开循环。
10. **Q：假死为什么不用 TCP keepalive / 不用 ping 超时？**
    A：WS 层已有心跳语义（`op=2`/`op=3`），服务端 60 s 无心跳会强制断开。
    再叠一层 keepalive 只是重复；关键是**判据要用心跳回应而不是消息到达**。
11. **Q：多房间会不会互相拖累？**
    A：每房间独立的任务/连接/会话；落盘按 `room_id` 分文件、SQLite 共库靠 `room_id`/`session_id` 区分。
    实测双房间并发（804456 + 7878）：两房间同时 `STREAMING`、重连各 0 次、会话互不相同。

### C. 存储与查询

12. **Q：为什么同时落四种格式？不是冗余吗？**
    A：各自的消费者不同：JSONL 给程序/可重放、CSV 给人/Excel、TXT 给词云/直接读、
    SQLite 给查询与面板。而且**四格式一致性本身就是一个验收手段**（互相比对能抓出写丢）。
13. **Q：游标分页的坑？**
    A：三处：①游标键必须**复合**（`recv_ts` 会并列，实测 393 组）；②`ORDER BY` 必须与游标键同键；
    ③响应必须瘦投影（否则触发 `SLOW_CONSUMER`）。
14. **Q：为什么不用 FTS5？**
    A：§6.4。中文 2 字关键词 + `unicode61`/`trigram` 都不合用，实测结论写在 `store.py` docstring。
15. **Q：`LIKE '%kw%'` 上百万行不就废了？**
    A：**这是本项目自觉的取舍**。当前量级（万行）够用；
    真要上量，路线图里已有三个候选方案（`trigram` + 2 字降级 / 自建 2-gram 倒排 / 维持 `LIKE` 只做范围收窄），
    并且**要求先有真实慢查询样本再动手**，而不是拍脑袋上 FTS。
16. **Q：怎么保证历史数据不被面板改坏？**
    A：`DanmakuStore` 以 `mode=ro` 打开。代价是它**不会跑迁移**，所以查询必须列自适应（D18）。

### D. 前端与产品

17. **Q：为什么历史浏览不做虚拟列表？**
    A：现在是"截断渲染最后 400 条 + 游标翻页"，对"回看某一段"这个真实场景够用。
    虚拟列表是另一个量级的复杂度，而**收益边界**没被验证过（面板的瓶颈是网络载荷与
    `SLOW_CONSUMER`，不是 DOM）。真要做，前置条件是先补组件级测试。
18. **Q：XSS 怎么防的？**
    A：**绝不 `v-html`**，关键词高亮走分段渲染；表情图片只接受 `http(s)`。
    手测清单里就有 `<img src=x onerror=alert(1)>` 这一条。
19. **Q：统计口径为什么有两种？**
    A：`window=0` = 自面板启动累计（来自 hub 内存计数，**不含历史补种与往次运行**）；
    `>0` = 最近时段（走 SQLite 补延迟分位与发言榜）。
    两种数字**不能混读**，所以侧栏标题带口径角标。

### E. 工程与方法论

20. **Q：覆盖率 90.76% 是怎么做到的？**
    A：口径明确（只算核心模块，`cli.py` 不计入）+ 门禁 85% + 全离线可跑 +
    真实抓包夹具 + 假服务端。**但我会主动说分模块最低值只有 71%（`collector.py`）**——
    连接状态机的故障路径更多靠真实压测与端到端验收保证。
21. **Q：你怎么知道它真的能用，而不是测试写得漂亮？**
    A：因为踩过四次"单测全绿但功能全废"（D12/D13/D15/D16），
    所以定了一条硬规矩：**每个里程碑都要做端到端验收**；
    并且明确了"编码问题只能看字节"这类断言纪律。
22. **Q：这个项目最大的技术风险是什么？**
    A：B 站协议漂移与风控升级。对策是 `raw` 全量 + 未知 cmd 兜底 + 双 token 路径 + 指标预警。
23. **Q：如果让你重做，会改什么？**
    A：（诚实答）会先补**保留策略**（现在 JSONL 永不清理、库单调增长）与
    **`collector.py` 的故障路径测试**；前端会在第一次大改前就补组件级测试；
    以及**跨进程单实例**（现在 CLI 面板与托盘面板可以同时写同一个库）。

### F. 边界与"不做"

24. **Q：为什么不做礼物/上舰？**
    A：这是需求方**明确拍板**的范围冻结（DEC-1）：按"无用户文字即排除"处理。
    被排除的事件**仍被接收并计数**，所以"漏了多少"是可观测的；
    要协议调试可以 `--all-events`。**代码层面无需改动**（过滤层本来就支持）。
25. **Q：为什么不做多平台？**
    A：**"先有第二个平台的真实需求，再抽接口"**。现在抽 `Adapter` 只会得到一个
    "只有一个实现、且为它量身定做"的假抽象 —— `api.py` 里的 `retry=1`、WBI 签名、
    `getConf` 降级、`-352` 黑名单**全是 B 站专有语义**，抽早了必然泄漏。
26. **Q：为什么不做 LLM 分析？**
    A：能力上不难，**但它是隐私基线的变更**。项目承诺"数据不出本机"，
    所以任何外发功能都要先过 **G4：书面隐私决策**（字段白名单 + 默认关闭 + 面板显式开关）。
    目前只做**本地纯统计**，这也是范围上的自觉。
27. **Q：为什么不做开机自启 / 系统服务？**
    A：DEC-5。崩溃只保证已落盘数据保留，由用户手动恢复 ——
    这是"个人工具"的定位，不是服务端产品。

### G. 打包与部署

28. **Q：exe 怎么发的？多大？**
    A：PyInstaller 单文件，`--windowed`，实测 **~26.9 MB**（`28,218,012 B`），构建约 24 s，
    冷启动 3.3–4.8 s。词云的重型依赖（matplotlib/numpy/wordcloud/jieba）**显式排除**。
29. **Q：为什么面板跑在托盘进程内，而不是 spawn 子进程？**
    A：①架构本来就支持（hub/panel/uvicorn 都是进程内对象）；
    ②停止仍走 `should_exit` → lifespan → 各房间 `bus.stop()` **flush 落盘**；
    ③**从架构上消解了"关掉终端连坐杀掉面板"这个平台缺陷**。
30. **Q：托盘为什么不用 `pystray`？**
    A：它的菜单能力不足（状态行/动态置灰/分隔符/默认项都要手搓），
    而纯 `ctypes` 已实测可用（`Shell_NotifyIconW` / `CreatePopupMenu` / `TrackPopupMenu` / 消息泵）。
    少一个依赖也少一份打包与环境风险。

### H. 工程化与流程（最容易被问倒的一类）

31. **Q：有 CI 吗？**
    A：**没有**，这是我最该补的一条（详见 §13 第 13 条）。
    测试已经做到全离线可跑、有覆盖率门禁，接一条 `pytest --cov` 就能守住了。
32. **Q：怎么保证改动没弄坏别的东西？**
    A：三层：①金样本回归（改 `parser.py` 前后必须过 `test_parser.py`）；
    ②不变量用例（游标"不重不漏"、背压"写入+丢弃==总接收"）；
    ③**每个里程碑做端到端验收**（因为踩过四次"单测全绿但功能全废"）。
33. **Q：`tools/` 里几十个脚本是不是技术债？**
    A：我把它们分三类：正式构建/验收（4 个）、一致性校验（把"用户报的 bug 修没修"变成可重复脚本）、
    一次性探针（**把猜变成实测**）。第三类看起来乱，但它产出的是**结论和修复**，
    而且每个都留下 docstring 记录实测事实。真正的问题是**没有 CI 让这些校验自动跑**。
34. **Q：项目里最体现你调试能力的一件事？**
    A："关掉终端面板也停"那条。**根因被推翻过一次**：第一版结论是 Job Object，
    被 `probe_job.py` 证伪；真因是 venv 的 `python.exe` 转发器 stub 多起了一个 base 解释器，
    Windows 因此分配了**新的 conhost**，关窗口连坐的是挂在该 console 上的真 server。
    修法是绕开 stub 直接起 base 解释器，并且把验证从"人工关终端"换成了三条**可自动化**的判据。

### 12.4 关于技术表述：几个容易讲错的点

1. **"protover=3 解压后就是 JSON"** ❌ —— 解压后**仍是带头部的包**，要递归拆。这是本项目反复强调的"必需而非优化"。
2. **"重连是因为没收到消息"** ❌ —— 判假死的依据是**没收到心跳回应**（`op=3`）。
   低热度房间消息稀疏是常态（实测 25 秒 11 条）。
3. **"队列满了就丢最新的"** ❌ —— 是**丢最旧**（保留最新）。
4. **"游标用 `recv_ts`"** ❌ —— 是 **`(recv_ts, id)` 复合游标**，且 `ORDER BY` 必须同键。
5. **"历史接口返回完整事件"** ❌ —— 是**瘦投影**；完整 `Event` 只属于 `/api/events` 与 `/api/export`。
6. **"`raw` 可以不要"** ❌ —— 它是协议漂移后**重新解析历史数据**的唯一依据，默认保留。
7. **"分析也在采集热路径上"** ❌ —— 只有**可加**的词频在热路径增量维护（47 µs/条）；
   跨片比较类指标（热点突增、账号画像）**在请求时算**。
8. **"标注表和采集数据放一个库更方便"** ❌ —— **刻意分开**：生命周期不同、`store.py` 只读、可单独删除。
9. **"`uid=0` 表示没有 uid"** ❌ —— 它是**被打码的匿名用户**；账号画像里要**排除**它，
   否则匿名用户会并成一个"用户 0"冲上榜首。
10. **"礼物金额和 SC 金额可以直接相加"** ❌ —— 单位不同（金瓜子 vs 元），**差 1000 倍**（这正是 D20）。

### 12.5 关于演示：不要现场联网

- 现场联网**依赖登录态凭据与 B 站可用性**，失败率不可控。
- **推荐演示路径**（全部离线）：
  `pytest` 全绿 → `npm test` → `bili-danmaku wordcloud --source data/xxx.jsonl`（离线读 JSONL）
  → `bili-danmaku stats`（读本地库）→ 打开已构建的面板或已打包的 exe 看历史浏览。
- 真要抓实时，**提前录屏**比现场赌网络稳。

### 12.6 关于"讲多少"：三个不要

1. **不要罗列功能**。面试官不关心你有 11 个子命令；关心你**为什么这么设计**。
2. **不要隐瞒薄弱点**。§13 列的都是会被追问的，主动说 = 加分，被问出来 = 减分。
3. **不要吹覆盖率**。说 90.76% 的同时说 `collector.py` 只有 71%，反而显得可信。

### 14.4 演示时的口径说明（很重要）

### 15.1 一页数字（背这些就够）

**协议**

- 包头：16 字节大端（`>IHHII`）；`op` 2/3/5/7/8；`protover` 0/1/2/3

**存储**

- 队列 20000；batch 200；flush 1 s；轮转 1 h / 128 MB

**Web / 前端**

- 端口 8787 → 8788…（自动）；hub 房间缓冲 2000；订阅者队列 500；慢客户端阈值 200；stats 推送 2 s

- 前端：实时缓冲 2000（进历史时 300）；渲染 400 条；历史窗口 1200

**分析**

- 窗口：≤1200 条原文 / 20 片 × 60 s / 每片 ≤2000 词 / 每片 ≤400 条原文
